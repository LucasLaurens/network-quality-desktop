Le domaine a aussi ses propres tests unitaires (notes, hystérésis, hors ligne, perte, et le reste) : la couverture de `domain` ne compte que les tests de la crate, pas ceux du moteur qui l'utilise.

Côté front, le faux client et les aperçus distribuent les textes des fenêtres depuis `tests/fakes/interface-texts.json`, écrit par le test Rust `exports_the_interface_texts_for_the_fakes` à partir du vrai catalogue : `pnpm bindings:check` échoue s'il diffère du fichier versionné, comme pour `src/bindings.ts`. Les tests montent les composants avec `mountWindow(composant, client)`, qui leur donne ce que `main.ts` leur donne en vrai (`createWindowProvisions`) et laisse arriver leurs premières lectures. Le faux client prend un objet d'options (`appInfo`, `display`, `windowModeTexts`, le reste généré) ; `createSettingsForm` est le formulaire d'un premier lancement, d'où part le faux et auquel les tests des réglages comparent. Le cache de modules de Vitest est coupé (`fsModuleCache: false`) : il indexait un fichier de test sur son seul contenu, si bien que les gardes qui listent les sources par `import.meta.glob` gardaient la liste vue la première fois.

Les faux en mémoire sont des implémentations concrètes des ports (`crates/application/src/test_support.rs`), jamais des mocks. Ils ne sont compilés que pour les tests, via la feature `test-support`. Chaque port a le sien, `NetworkChangeWatcher` et `PowerEventSource` compris (`InMemoryNetworkChangeWatcher`, `InMemoryPowerEventSource`) : le shell branche les vrais par `EngineInbox::follow_system_events`, que ses tests pilotent avec ces faux (un changement de réseau, une veille puis un réveil arrivent au moteur). Le moteur lui-même ne les connaît pas : il reçoit leurs avis comme des messages (`NetworkChanged`, `Sleep`, `Wake`), que ses tests envoient directement.

Les données qu'un test utilise sans les tester sont générées avec la crate `fake` : noms de réseau (`generate_network_name`), cibles de mesure et serveur personnalisé (`generate_targets`, toujours distincts). Le moteur, la sonde et les dépôts ne dépendent donc d'aucune valeur particulière. Les adresses de box sont générées aussi (`generate_address`). Restent écrites les valeurs de contrôle : seuils, durées proches d'une limite, cas limites du CSV (guillemets, formule), et l'adresse MAC d'une passerelle, écrite par son dernier octet (avec, dans les tests du moteur et de l'historique, l'adresse IP qui en découle) : c'est l'identité d'un réseau, que les tests comparent pour dire s'il s'agit du même réseau ou d'un autre.

## Preuve que les tests détectent les erreurs

Chaque règle a été cassée volontairement pour vérifier qu'un test échoue : délais d'hystérésis raccourcis (2 tests rouges), p50 au lieu de p90 (3 tests rouges), couleur modifiée dans `tokens.css` (1 test rouge), seuil de bascule TCP abaissé (2 tests rouges), cible injoignable classée « perdue » (1 test rouge), perte notée dès la première sonde (1 test rouge), gigue calculée sur la médiane des cibles (1 test rouge), « 60s » ou « 5% » dans le catalogue (1 test rouge chacun), retour au calme diagnostiqué « hors seuils » (1 test rouge), affichage écrasé par une première lecture arrivée en retard (1 test rouge), constat retiré du menu (1 test rouge), partage de connexion déduit d'un seul indice (2 tests rouges), contexte relu à chaque seconde ou jamais au premier tick (1 test rouge chacun), contexte non relu après une coupure (1 test rouge), indice « connexion payante » ignoré (1 test rouge), changement de réseau jamais constaté (2 tests rouges). Cinq cas tirés des revues ont d'abord été écrits en rouge : nouveau réseau après un instant sans route, MAC de passerelle résolue tard, partage reconnu tard, autre box à la même adresse IP, partage compté limité malgré le système. Attribution : diagnostic Hors ligne figé (2 tests rouges), tronçon toujours attribué à l'opérateur (4 tests rouges), tronçon en cause absent du chemin (2 tests rouges), passerelle pingée sous VPN (1 test rouge). Les revues ont ajouté : un seul ping perdu pardonné, lien très instable jugé sur ses pertes, attente de 10 pings, box mesurée pendant une coupure, état Solide malgré un lien lent vers la box. Wi-Fi : signal faible nommé comme cause, signal ignoré quand un câble porte le trafic, nom masqué avec lien pour le révéler, conseil « 5 GHz » réservé à la 2,4 GHz, échelle de force de NetworkManager, canal 6 GHz 2. Historique : minute non fusionnée en SQLite (contrat rouge), heure fermée à la mauvaise minute (1 test rouge). Ajoutés après les revues : heure d'un réseau quitté avant sa fin, minutes d'une heure non conservée gardées par la purge, secondes avant tout réseau, MAC apprise gardée, pas de gigue à travers un trou, journal d'une base abîmée gardé, base d'une version plus récente laissée intacte.

## Aperçu visuel

Deux pages hors build, servies par `pnpm dev:web`, affichent les écrans avec des données préparées : `tests/preview/popover.html` (`?scenario=degraded`, `offline` ou `undetermined` pour l'aide au ping, `?tests=on` pour un test de débit) et `tests/preview/dashboard.html` (`?scenario=window` pour la note du mode fenêtre, `undetermined` pour l'aide au ping).

`pnpm screenshots` (`scripts/capture-screenshots.mjs`, `pnpm dev:web` lancé) refait les captures du README dans `docs/images/` à partir de ces pages, en clair et en sombre, aux tailles de `tauri.conf.json` et en double densité : des données fictives, jamais un vrai nom de réseau. La page du tableau de bord affiche la vraie version, lue dans `package.json`.

`pnpm test:visual` (Playwright, `playwright.config.ts`, `tests/visual/layout.pw.ts`) les mesure dans Chromium, en thème clair puis sombre, aux tailles de `tauri.conf.json` : le popover à 320 × 560 dans ses trois scénarios, le tableau de bord et les Réglages en plein écran (1920 × 1080), à 960 × 720 et à leur taille minimale, 640 × 480. Tout ce qui est replié est déplié avant la mesure. Le test échoue si la page défile de côté, si un élément dépasse le bord de la fenêtre sans qu'une boîte contenue dans la fenêtre le coupe (une zone qui défile, par exemple), si une boîte qui coupe son contenu en cache une partie, si le popover replié ne tient pas dans ses 560 pixels de haut, si les sections du tableau de bord ou les lignes des Réglages ne sont pas alignées à gauche, ou ne finissent pas au même bord droit que les onglets, si la colonne n'est pas centrée dans une fenêtre plus large qu'elle, ou si le fond ne suit pas le thème demandé. La CI le lance à chaque PR sur Ubuntu, macOS et Windows (job « Mise en page »), car la hauteur d'un texte dépend des polices du système. Le popover n'est mesuré que sur macOS et Windows : sous Linux, la pastille ouvre un menu à sa place (`grepInvert` dans `playwright.config.ts`). Remettre les commandes de l'aide au ping sur une seule ligne le fait échouer, elles dépassent du popover ; une marge de 400 pixels sur l'aide aussi, il ne tient plus en hauteur. L'alignement des sections du tableau de bord est une garde contre une marge ajoutée à l'une d'elles ; celui des lignes des Réglages est le plus parlant. Restent à l'œil : le focus visible au clavier et le dessin des rayons.

## Tests de fumée

`pnpm test:smoke` (`crates/infrastructure/tests/smoke.rs`, ignorés par défaut) lance les vrais adaptateurs du système qui l'exécute, chacun sur son propre fil, et vérifie que chacun répond en moins de 10 secondes (un adaptateur bloqué fait échouer le test sans le figer ; la CI coupe un job au-delà d'une heure) : la sonde atteint une cible par ICMP ou par son repli TCP (les machines de CI bloquent souvent l'ICMP), le contexte de connexion trouve la route par défaut, le lecteur Wi-Fi répond (sans Wi-Fi sur une machine de CI), l'horloge avance et suit l'heure du système, la barre système répond (présente hors Linux). Le job « Qualité » les lance sur macOS, Linux et Windows. Réduire le délai à une microseconde en fait échouer trois.

| Système                            | Attendu                                                                                                                                   | Dernière vérification |
| ---------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------- | --------------------- |
| macOS                              | Événements `sleep` puis `wake` dans l'historique ; minute d'avant la veille écrite ; « Retour de veille » au réveil ; trou dans la courbe | pas encore vérifié    |
| Windows (veille classique)         | Idem                                                                                                                                      | pas encore vérifié    |
| Windows (Modern Standby)           | Idem, ou au moins « Retour de veille » par le filet du trou de mesure si l'avis ne vient pas                                              | pas encore vérifié    |
| Linux avec logind (Ubuntu, Fedora) | Idem ; `systemd-inhibit --list` montre le verrou « Qualité de connexion » en mode `delay`                                                 | pas encore vérifié    |
| Linux sans logind                  | « Retour de veille » par le filet du trou de mesure ; message « Watching sleep through logind failed » dans le journal                    | pas encore vérifié    |
